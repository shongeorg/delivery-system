# User stories і сценарії

Легенда: ✅ реалізовано й перевірено, 🟡 реалізовано частково, ❌ немає.

## Клієнт

### US-1. Знайти страву і додати в кошик ✅

1. Відкриває `/` — категорії та 103 страви з пагінацією.
2. `/catalog`, `/category/:slug`, `/product/:slug` — фільтрація й картка страви.
3. «Add to Cart» → `POST /cart/items`; бейдж у хедері показує кількість.
4. `/cart` — зміна кількості (`PATCH`), видалення, очищення.

Критерій: після додавання позиція видна в кошику після перезавантаження сторінки.

### US-2. Оформити замовлення ✅

1. `/checkout` показує позиції, суму, тип доставки, адресу й телефон (підставляються з профілю).
2. «Use my location» — запит геолокації; без неї бекенд геоко­дить адресу.
3. Оплата: картка (Stripe Elements) або готівка.
4. Submit → `POST /orders` → редирект на `/orders?success=1&order=<id>`.

Критерій: замовлення з'являється в «My Orders», у кухні й у кур'єрському списку після `ready`.

Обмеження: точка доставки може бути відсутня, якщо і геолокація, і геокодинг не дали результату.

### US-3. Бачити статус і кур'єра ✅

1. `/orders` — список із посиланням «Track order» / «Details».
2. `/orders/:id` — таймлайн, карта, картка кур'єра, «Courier position updated».
3. Оновлення: WS `order:<id>` + полінг 5 с.

Критерій: після прийняття замовлення кур'єром статус змінюється без ручного перезавантаження, а маркер кур'єра рухається при нових координатах.

Обмеження: якщо кур'єр не має геолокації, маркера немає — лише адреса.

### US-4. Написати кур'єру або підтримці ✅

1. На `/orders/:id` — блок чату.
2. `POST /chats/order/:orderId/messages` → повідомлення в каналі `order:<id>`.
3. Кур'єр бачить його у своїй картці «Chat», адмін — через API.

Критерій: повідомлення зберігається і видно іншій стороні після оновлення або миттєво через сокет.

### US-5. Скасувати замовлення ✅

`POST /orders/:id/cancel` доступний, поки статус `created` або `paid`. Після `cooking` — `400`.
UI: окремої кнопки скасування немає (лише API).

### US-6. Поскаржитися/оцінити ❌

`/reviews` API є, UI відгуків на сторінці страви відсутній.

## Кур'єр

### US-7. Побачити доступні доставки ✅

`/orders` у `courier-app`: вкладки Available (`ready`), Active (`on_the_way`), Completed (`delivered`), статистика, автоперезавантаження 15 с.

Обмеження: список **не** фільтрується за кур'єром — це всі доставки системи.

### US-8. Прийняти замовлення ✅

«Accept & pick up» → `PATCH /orders/:id/status { on_the_way }`. Бекенд перевіряє, що замовлення `ready` і не призначене іншому; записує `courierId`.

Критерій: другий кур'єр отримує `409` і не може перехопити замовлення.

### US-9. Побачити маршрут до клієнта 🟡

`/orders/:id` → кнопка «Route» → `/orders/:id/map`: маркери кур'єра й клієнта, лінія OSRM, відстань, ETA, кнопка «Share my location».

Обмеження: без дозволу на геолокацію власна точка відсутня → маршрут не будується (у тестовому браузері геолокація `denied`).

### US-10. Оновлювати позицію ✅

`watchPosition` → `courier_location_update` (WS) + `PUT /orders/:id/location` (HTTP), не частіше ніж раз на 8 с.

### US-11. Завершити доставку ✅

«Mark as delivered» → `PATCH /orders/:id/status { delivered }`. Показується банер «Delivered».

### US-12. Спілкуватися з клієнтом ✅

Картка «Chat» на `/orders/:id`: історія, відправка, живі оновлення через `chat_message`.

### US-13. Подзвонити клієнту ✅

Кнопка `Call` → `tel:` (PSTN). WebRTC-дзвінка немає: WebSocket зараз не виконує роль сигналізації.

## Кухня (`сhef-panel`)

### US-14. Бачити чергу ✅

`/` — New / Waiting / Cooking / Ready, низький залишок; `refetchInterval: 5000`.

### US-15. Прийняти в роботу і позначити готовим ✅

«Accept & Start Cooking» → `cooking`. «Mark as Ready for Courier» → `ready`, після чого замовлення з'являється в кур'єра.

Перевірено в браузері: `created → cooking → ready`.

### US-16. Керувати рецептами й складом ✅

`/recipes`, `/inventory` — CRUD через `/inventory` та `/products`.

## Власник (`ower-panel`)

### US-17. Дашборд ✅

`/` — дохід (today/week/month), чистий прибуток, активні замовлення, середній чек, персонал, топ-продукти, низький залишок. `refetchInterval: 15000`.

### US-18. Персонал і зарплати ✅

`/staff` (33 акаунти), `/staff/:id` — роль, блокування, базова ставка, бонус, валюта; `/payroll` — виплати й бонуси. Усі зміни пишуться в `audit_logs`.

### US-19. Фінанси ✅

`/finances` — дохід (лише `paid`), payroll, витрати, чистий прибуток, денний графік, створення/видалення витрат.

### US-20. Кухня й кур'єри ✅

`/kitchen` — черга за статусами, час очікування, **призначений кур'єр** (ім'я, телефон) для `on_the_way`.

Обмеження: живої карти кур'єрів у owner-панелі немає; позиція доступна через `GET /orders/:id/tracking` (роль owner дозволена), але UI її не показує.

### US-21. Налаштування й аудит ✅

`/settings` — назва, телефон, адреса, години, валюта, податок, доставка. `/audit-logs` — журнал дій.

### US-22. Чат з клієнтами 🟡

API дозволяє owner/admin читати й писати в чат замовлення; окремого екрана в owner-панелі немає.

## Наскрізні сценарії (перевірені)

### E2E-1. Повний цикл доставки ✅

1. Клієнт оформлює замовлення (cash) з адресою → `created`.
2. Кухня: `cooking` → `ready`.
3. Кур'єр: приймає → `on_the_way`, `courierId` записаний.
4. Кур'єр надсилає локацію → клієнт бачить маркер.
5. Кур'єр: `delivered` → клієнт бачить завершений таймлайн.
6. Owner-панель: замовлення з кур'єром у `/kitchen`.

### E2E-2. Сесія протухла ✅

`courier-app`: підміна access-токена на невалідний → `GET /orders` 401 → `POST /auth/refresh` 200 → повторний `GET /orders` 200, список на місці.
Якщо невалідний і refresh → `logout()` і редирект на `/`.
Аналогічно поводяться `frontend`, `сhef-panel`, `ower-panel`.

### E2E-3. Чат між клієнтом і кур'єром ✅

Клієнт (або адмін у клієнтському UI) пише → `201`, `sender` визначений роллю; кур'єр бачить повідомлення у своїй картці; owner отримує `chat_message` через WS.

## Відомі прогалини

- Немає окремої адмін-панелі: роль `admin` входить у owner-панель, але UI-гард пускає лише `owner`.
- Немає WebRTC-дзвінка (див. нижче), лише `tel:`.
- Немає історії переміщень кур'єра (тільки остання точка).
- Немає «оплачено готівкою» → такі замовлення не потрапляють у дохід.
- Немає UI відгуків.
- Немає транзакційного захисту від одночасного прийняття замовлення двома кур'єрами.

## Про WebRTC (дзвінок через інтернет)

Технічно можливо, але WebSocket — не транспорт для дзвінка:

- **WebSocket** передає лише сигналізацію: `call_offer`, `call_answer`, `ice_candidate`, `call_hangup`. Інфраструктура вже є (`broadcastToUser`, канали, авторизація).
- **Медіа** йде окремо: WebRTC (SRTP/DTLS) напряму між клієнтом і кур'єром.
- Потрібен **STUN** (визначення публічної адреси) і **TURN** (ретрансляція за симетричним NAT). Публічний STUN безкоштовний, TURN — це сервер і трафік, тобто гроші.
- `getUserMedia` працює лише в **secure context**: `https://` або `localhost`. На `http://192.168.x.x` мікрофон недоступний.
- Потрібні UI-стани: виклик, дзвінок, відхилення, завершення, дозволи — плюс обробка мобільних обмежень (фон, блокування екрана, iOS Safari).

Тобто дзвінок — це окрема фіча: сигналізація через наявний WS + TURN-сервер + нові екрани в обох застосунках.
